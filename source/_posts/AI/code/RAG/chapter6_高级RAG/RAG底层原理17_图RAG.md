# 前言：

传统 RAG 靠"向量搜索 + 拼上下文"已经能解决大部分问答场景了，但碰到多跳推理、跨文档关联这类"连线题"就开始拉胯。根本原因是：**向量检索只看语义相似度，不建模实体之间的关系**。GraphRAG（图 RAG）的核心思路就是——用知识图谱把实体和关系显式地连起来，让检索从"找相似文本块"升级成"在图上找路径"。

# 传统 RAG 到底差在哪？

先搞清楚为什么需要图，才知道图解决了什么问题：

| 传统 RAG 的痛点 | 具体表现 |
|---|---|
| **关系理解缺失** | 向量检索只关注语义相似度，碰到"A 收购了 B，B 的母公司是 C"这种多实体关联就断链 |
| **上下文碎片化** | 文本被切成独立 Chunk，跨文档/跨章节的信息整合能力极差 |
| **检索噪声→幻觉** | 召回了不相关或半相关的文本块，反而干扰 LLM 判断，诱发胡编 |
| **推理能力有限** | 只能基于线性文本做推理，不支持多跳逻辑导航 |
| **实体歧义** | 同名不同义（"苹果"是公司还是水果？）、别名/缩写/多语言变体，向量相似度搞不定 |
| **时效性不足** | 文本块没有可计算的时间属性，问"某公司2021年是否还是子公司"这种时序问题就懵了 |

一个经典例子：

> 问题："2019年收购A公司的企业，其母公司在2021年的主要投资对象是谁？"

传统 RAG 需要检索多段文本并在生成阶段自行拼接推理，任何一段缺失或存在歧义，整条推理链就断了。而知识图谱天然能沿着 `收购→母公司→投资` 这条路径走下去。

---

# 知识图谱凭什么能救场？

知识图谱用**节点（实体）** 和**边（关系）** 把离散的知识编织成一张网。核心优势四个字：**显式连接**。

- **结构化语义表达**：直接编码 `公司A -[收购]→ 公司B` 这种显式关系，不需要 LLM 从文字里猜
- **天然支持多跳推理**：沿图路径遍历，间接但关键的知识关联都能发现
- **事实性 + 可解释性**：答案可以追溯图中的推理路径，有理有据，抑制幻觉
- **异构数据集成**：结构化（数据库）和非结构化（文本）数据都能往图里塞，形成统一知识视图

进阶能力：
- **本体约束**：通过 Schema 和 Ontology 约束推理空间，降低歧义
- **溯源管理**：边和节点可以带来源、时间戳、置信度，方便冲突消解
- **时间建模**：支持时间态边和版本化节点，可以做"某年某公司还是不是子公司"这种时间旅行查询

# GraphRAG 通用架构（三阶段）

不管哪个框架，GraphRAG 基本都是三步走：**构建图谱 → 图谱检索 → 增强生成**。

![](https://datawhalechina.github.io/all-in-rag/chapter7/images/7_1_1.svg)

---

## 知识图谱构建

这是整个 GraphRAG 的地基，质量决定上限：

- **知识抽取**：用 LLM 或 IE 管线从文本中抽取实体、关系和属性（含指代消解、别名归一、术语标准化）
- **质量控制**：对三元组做置信度评估、人机协同抽检、冲突消解，必要时用规则和本体约束做一致性校验
- **图谱融合**：跨来源的实体对齐与去重（Entity Resolution），合并时保留溯源信息
- **存储与索引**：落地到图数据库（Neo4j / NebulaGraph / TigerGraph 等），建立属性和关系索引

## 图谱检索

这一步是和传统 RAG 差别最大的地方——不再是简单的向量相似度搜索，而是**在图上做结构化查询**：

1. **实体定位**：先用实体链接或向量检索在图中锁定核心实体节点
2. **子图探索**：从命中节点出发，用图查询语言（Cypher）或遍历算法做邻域扩展、路径发现、约束过滤（限定关系类型、跳数、时间区间、置信度阈值）
3. **结构化证据抽取**：将路径和关键节点属性序列化为可读证据片段，或生成子图的文本摘要
4. **高级检索**：如社区检测（Leiden）生成多层次摘要，实现"全局-局部"联合检索

Cypher 查询示例——查询公司A两跳内的收购路径及目标行业：

```cypher
MATCH (a:Company {name: "A"})-[:ACQUIRED]->(b:Company)-[:IN_INDUSTRY]->(i:Industry)
RETURN a.name AS acquirer, b.name AS target, i.name AS industry
UNION
MATCH (a:Company {name: "A"})-[:ACQUIRED]->(:Company)-[:ACQUIRED]->(b2:Company)-[:IN_INDUSTRY]->(i2:Industry)
RETURN a.name AS acquirer, b2.name AS target, i2.name AS industry;
```

## 增强生成

把检索到的结构化知识（实体属性、关系路径、子图摘要等）和原始查询一起注入 Prompt：

- **提示设计**：明确要求模型引用"图证据"，在回答中给出来源与路径
- **证据融合**：结构化三元组/路径 + 原文片段联合提供，兼顾事实性和文本细节
- **约束回答**：敏感领域（金融/医疗）可采用模板化输出 + 字段校验，进一步减少幻觉

# 方法论分类

根据知识图谱与 RAG 的结合深度，现有方法大致分三类：

| 类型 | 核心思路 | 优势 | 劣势 |
|---|---|---|---|
| **知识驱动型** | 检索过程完全依赖图谱，文本转 Cypher/Gremlin 在图上直接查询推理 | 高精度、高可解释性 | 受限于图谱完备性，覆盖和容错差 |
| **索引驱动型** | 把图谱的结构信息融入文本索引（如用邻居实体/关系做元数据特征，子图摘要拼接后再向量化） | 集成成本低 | 显式推理弱，可解释性一般 |
| **混合型** | 同时用图检索和文本检索，对结果统一重排融合 | 综合表现最稳健 | 系统复杂度和工程成本较高 |

实践中混合型是主流趋势——简单事实问答优先图检索，叙事性问题补充文本证据，复杂查询先在图上定位路径再以路径节点为"导航枢纽"做针对性文档检索。

# 主流框架对比

## Microsoft GraphRAG

重量级框架，核心理念是"**先构建全局知识，再按需检索**"：

- 文本 → 三元组/子图构建 → 属性图
- 采用社区检测（Leiden算法）进行图划分，按层级生成全局/社区/局部摘要
- 查询时先匹配全局/社区摘要，再下钻到局部子图与原文证据
- 返回"全局观 + 证据路径"并行的双视角答案

**优势**：强全局感知、良好可解释性，适合探索性分析和全景总结。
**代价**：前期构建和分层摘要成本较高，对数据持续变更需设计增量更新策略。

## LightRAG

针对 GraphRAG 的"重量"问题，追求**轻量、高效、易扩展**：

- "双层检索"与"图增强索引"，以较低构建成本获得全局-局部兼顾的检索能力
- 强调将结构信号嵌入到文本索引与重排中，弱化复杂的社区发现流程
- 适用于资源受限、快速迭代与在线更新场景

## FRAG（Flexible RAG）

强调"**灵活性与模块化**"，自适应不同复杂度的查询：

- 查询分流：通过分类器或规则将请求判定为简单/复杂
- 简单查询：直接实体链接 + 属性查找，低延迟返回
- 复杂查询：激活路径检索/多跳推理模块，再融合文本证据
- 模块化设计，迁移成本低

## GraphIRAG（迭代检索）

引入"**迭代检索**"思想，认为单次检索不足以解决复杂问题：

- 由控制器在生成过程中多轮触发图查询，逐步补齐证据链
- 以"新信息增益"为准则决定是否继续迭代以及何时停止
- 对时间敏感和多跳推理任务更具鲁棒性

# 评估体系

GraphRAG 的评估是多维度的，比传统 RAG 多了图特有的维度：

## 核心评估指标

**检索质量：**
- 传统：Precision、Recall、F1、Hit Rate@K
- RAG 特有：
  - 上下文精确率 = 检索到的上下文中"真正相关"的比例
  - 上下文召回率 = 所有应当支持答案的"金标准证据"被检回的比例
  - 引用/归因准确率 = 生成答案中的关键断言是否被检索证据正确支撑

**生成质量：**
- 问答：精确匹配（EM）、F1
- 摘要：ROUGE
- 事实一致性/忠实度（Faithfulness）：断言与证据的一致性

**系统性能：**
- 推理延迟（Latency）、吞吐量（QPS）、成本（API 调用次数、GPU/内存消耗）

## 常用基准数据集

| 任务类型 | 代表数据集 | 说明 |
|---|---|---|
| **多跳问答** | HotpotQA、2WikiMultihopQA、MuSiQue | 要求在多个知识源之间推理，是 GraphRAG 核心能力的试金石 |
| **复杂问答** | WebQSP、ComplexWebQuestions (CWQ) | 包含结构复杂的查询 |
| **知识图谱QA** | KGQAgen-10k | 专门评估知识图谱问答能力 |

> ⚠️ 部分现有基准（如 WebQSP）存在数据质量问题或评估方法过于僵化（如严格的 EM），可能导致对模型性能的低估。构建更高质量的基准是未来的重要方向。

# 生产环境的现实挑战

把 GraphRAG 从实验室推向生产，面临的坑比传统 RAG 多不少：

- **知识图谱的构建与维护**：高质量图谱本身就是知识工程的苦活，生产环境还要求动态更新——增量更新机制是核心难点
- **系统性能与可扩展性**：知识库规模和查询量增长后，延迟、吞吐和资源消耗成为主要瓶颈（向量化慢、内存溢出、API 挂了都是常见问题）
- **安全与隐私**：引入外部数据源意味着新的攻击面——数据隐私泄露、模型中毒、检索模块被攻击
- **成本控制**：大规模部署需要大量计算和存储资源，架构优化以降低运营成本是重要的商业考量

---

# 总结：

这一节的核心脉络：

- **为什么要图 RAG**：传统 RAG 的向量检索搞不定多跳推理、实体关系和跨文档关联
- **图 RAG 怎么做**：构建知识图谱 → 图谱检索（实体定位 + 子图探索 + 证据抽取）→ 增强生成
- **三种结合深度**：知识驱动（纯图查询） / 索引驱动（图信号嵌入文本索引） / 混合型（图 + 文本双路检索），混合型是主流
- **主流框架**：Microsoft GraphRAG（重但全）、LightRAG（轻量）、FRAG（灵活模块化）、GraphIRAG（迭代检索）
- **落地挑战**：图谱构建维护贵、性能扩展难、安全隐私风险、成本高

简单说，GraphRAG = **用知识图谱给 RAG 装上了"关系推理引擎"**。适合多跳问答、事实性要求高、需要可解释性的场景。但代价是工程复杂度上了一个台阶。
